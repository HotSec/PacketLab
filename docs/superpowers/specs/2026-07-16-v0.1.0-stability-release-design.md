## 1. 背景与目标

### 1.1 背景

PacketLab 已交付 V3 计划核心功能（代理 + MITM + 拦截 + 网卡抓包 + 进程关联 + LLM 解析 + HAR 导出），代码组织清晰。但代码审查发现：

- **4 个 P0 级数据正确性 bug**：代理 body 截断、SaveBatch 失败处理、MITM 黑名单失效、manual 模式 body 丢失
- **5 个 P1 级稳定性/安全 bug**：MemRingBuffer race、死锁风险、goroutine 泄漏、ListHosts 性能、WebSocket Origin 校验
- **6 个 P2 级体验/边界问题**：limit clamp、Upgrade 失败处理、重试退避、ring 容量参数化、统计一致性、并发安全
- **CI 完全缺失测试阶段**：仅 release.yml 在 tag 触发时构建，无 test/vet/lint
- **测试盲区**：`proxy.go`、`batch.go`、`mitm.go`、`ws.go` 零单元测试
- **V3_PLAN 未完全落地**：`--capture-max-streams`、拦截规则前端 UI、参数化超时等
- **文档脱节**：CHANGELOG 停留在 v0.0.2，README/V3_PLAN 未反映 LLM 模块等增量

### 1.2 目标

交付 **v0.1.0 — 修复已知 bug、重构稳定性问题、补齐 V3_PLAN、建立 CI、同步文档**，使项目达到"完善可用版本"状态。

### 1.3 非目标（推迟到阶段二）

- LLM 扩展（自定义 OpenAI 兼容端点、扩充提供商、成本分析、Tool/Function Calling 结构化）
- 1Gbps/2.5Gbps 性能优化（多 worker pipeline、sharded stream、零拷贝 HTTP 解析）
- 物化 `host_summary` 表 + trigger 维护

### 1.4 交付节奏

采用「方案 A：分层递进 + 增量交付」，分 4 个独立 PR：

## 2. PR-1：P0 Bug 修复

### 2.1 Bug 1：代理转发请求体/响应体被截断

**位置**：`internal/proxy/proxy.go:113-121`、:172-173

**根因**：`io.LimitReader(req.Body, maxReqBytes+1)` 读取后用截断的 `bodyBytes` 替换 `req.Body` 转发，客户端发的剩余 body 丢失。10MB POST 只转发 2MB。

**修复方案**：双路读取，全量转发 + 截断存储。

```go
// 请求侧
fullBody, err := io.ReadAll(req.Body)
if err != nil { /* log + 502 */ }

// 转发完整 body
req.Body = io.NopCloser(bytes.NewReader(fullBody))
req.ContentLength = int64(len(fullBody))
req.GetBody = func() (io.ReadCloser, error) {
    return io.NopCloser(bytes.NewReader(fullBody)), nil
}

// 存储侧取截断
storeBody := fullBody
if len(storeBody) > maxReqBytes {
    storeBody = storeBody[:maxReqBytes]
}
```

响应侧同理。代价是峰值内存 = `2 * maxBody`，与原代码持平（原代码也是 ReadAll）。

**测试**：
- `TestProxy_ForwardsFullRequestBody` — 10MB POST，断言上游收到完整 10MB
- `TestProxy_ForwardsFullResponseBody` — 10MB 响应，断言客户端收到完整 10MB
- `TestProxy_StoresTruncatedBody` — 10MB POST + maxReqBytes=2MB，断言存储 = 2MB

### 2.2 Bug 2：SaveBatch 部分失败时 ids 误用

**位置**：`internal/store/store.go:220-270`、`internal/proxy/batch.go:93-103`

**根因**：tx.Rollback 后仍返回 ids 数组，调用方收到 err 后仍触发 onSave。

**修复方案**：
- `store.go SaveBatch` 失败时 `return nil, err`，ids 设为 nil
- `batch.go` 收到 err 后 `continue`，仅记录错误日志，跳过 onSave
- 监控指标 `store.batch_errors` +1

**测试**：
- `TestSaveBatch_PartialFailure` — 注入第 K 条 INSERT 失败，断言 err ≠ nil 且 ids == nil
- `TestBatch_OnSaveNotCalledOnError` — 调用方收到 err，断言 onSave 回调未被触发

### 2.3 Bug 3：shouldMITM 端口后缀匹配失效

**位置**：`internal/proxy/proxy.go:261-283`

**根因**：`host` 含 `:443`，`HasSuffix` 永远不匹配 `.wns.windows.com`。

**修复方案**：先 `net.SplitHostPort` 去端口（容错 fallback 到原 host），再匹配。封装 `matchSkipHost(host string) bool` 函数。

```go
func matchSkipHost(rawHost string) bool {
    host := rawHost
    if h, _, err := net.SplitHostPort(rawHost); err == nil {
        host = h
    }
    for _, suffix := range mitmSkipSuffixes {
        if strings.HasSuffix(host, suffix) || host == suffix {
            return true
        }
    }
    return false
}
```

**测试**：表驱动 `TestMatchSkipHost` 覆盖：
- `abc.wns.windows.com:443` → true
- `abc.wns.windows.com` → true
- `cdn.apple.com:443` → true
- `api.example.com:443` → false
- `push.microsoft.com:443` → false
- `1.2.3.4:8080` → false

### 2.4 Bug 4：manual 模式 readBody 返回空字符串

**位置**：`internal/proxy/interceptor.go:306-321`、:197-205

**根因**：`OnRequest` 用 `io.NopCloser` 替换 `req.Body`，`NopCloser` 未实现 `GetBody`，`readBody` 走 false 分支返回 `""`。

**修复方案**：在 `proxy.go` 读取 body 后设置 `req.GetBody`（与 Bug 1 修复合并实现）：

```go
req.Body = io.NopCloser(bytes.NewReader(fullBody))
req.GetBody = func() (io.ReadCloser, error) {
    return io.NopCloser(bytes.NewReader(fullBody)), nil
}
req.ContentLength = int64(len(fullBody))
```

`readBody` 优先尝试 `req.GetBody()` 读取，fallback 到 `req.Body`。

**测试**：
- `TestInterceptor_ManualMode_PendingBody` — manual 模式拦截 POST，断言 pending.Body == 原始 body

## 3. PR-2：P1 Bug 修复 + 重构

### 3.1 Bug 5：MemRingBuffer 数据竞争

**位置**：`internal/capture/memring.go:47-90`

**根因**：`head/tail` 用 atomic，但 `r.buf[head] = Record{...}` 是普通写，跨核可见性无保证；Push 与 PopBatch 同时修改 tail 存在 lost update。

**重构方案**：放弃 lock-free，改用 `sync.Mutex` + `sync.Cond`。

```go
type MemRingBuffer struct {
    mu     sync.Mutex
    cv     *sync.Cond
    buf    []Record
    head, tail uint64
    mask   uint64
    overwrites atomic.Uint64
    closed bool
}
```

理由：原 lock-free 仅在 SPSC 才成立，当前 AsyncWriterPool 多生产者场景必加锁。性能损耗在 mutex 自旋，远小于 SQLite 写入。

**测试**：
- `TestMemRingBuffer_Concurrent` — 8 producer + 1 consumer，`-race` 跑 1s 无告警
- `TestMemRingBuffer_PushAfterClose` — 返回 false
- `TestMemRingBuffer_Overwrite` — 满时正确淘汰旧记录，overwrites 计数 +1
- `TestMemRingBuffer_PopBatchBlocked` — 空时 PopBatch 阻塞，Push 后唤醒

### 3.2 Bug 6：HandleClose / FlushOlderThan 锁顺序相反

**位置**：`internal/capture/engine.go:746-786`、:535-557

**根因**：`HandleClose` 锁序 `s.mu → a.mu`，`FlushOlderThan` 锁序 `a.mu → s.mu`，跨 worker 并发可能死锁。

**重构方案**：统一锁顺序为 **`a.mu → s.mu`**。

```go
// HandleClose
func (s *streamPool) HandleClose(...) {
    s.assembler.mu.Lock()
    defer s.assembler.mu.Unlock()
    delete(s.assembler.streams, key)
    s.mu.Lock()
    s.stats.StreamsClosed.Add(1)
    s.mu.Unlock()
}

// FlushOlderThan — 保持现有锁序
```

给 `Assembler` 增加注释明确锁顺序约定。

**测试**：
- `TestStreamPool_LockOrder` — `-race` 下并发调用 `HandleClose` × `FlushOlderThan` 1000 次，用 context 超时检测死锁

### 3.3 Bug 7：Interceptor logCh goroutine 泄漏

**位置**：`internal/proxy/interceptor.go:70-78`

**根因**：`for log := range it.logCh` 永远阻塞，进程退出前未刷盘。

**重构方案**：
- `Interceptor` 新增 `Stop()` 方法
- `startLogWriter` 启动时 `it.wg.Add(1)`，退出时 `it.wg.Done()`
- `Stop()` 顺序：先 `close(it.logCh)` 让 `for range` 退出，再 `it.wg.Wait()` 等待 goroutine 真正退出（顺序不能颠倒，否则 Wait 永久阻塞）
- `main.go` graceful shutdown 中 `interceptor.Stop()` 先于 `apiSrv.Stop()` 调用
- 用 `sync.Once` 保护 `Stop()` 幂等

```go
func (it *Interceptor) Stop() {
    it.stopOnce.Do(func() {
        close(it.logCh)   // 让 for range 退出
        it.wg.Wait()      // 等 goroutine 退出，期间会处理完 channel 中残留的 log
    })
}
```

**测试**：
- `TestInterceptor_Stop_FlushesLogs` — 注入 100 条 log，调用 Stop，断言全部落库
- `TestInterceptor_Stop_Idempotent` — 重复调用 Stop 不 panic（sync.Once 保护）

### 3.4 Bug 8：ListHosts 全表扫描两次

**位置**：`internal/store/store.go:747-807`

**根因**：两次全表扫描无分页，大表卡顿阻塞 dbRO。

**测试**：

## 7. 风险与缓解

### 7.1 MemRingBuffer 重构可能影响性能

**风险**：从 lock-free 改为 mutex，可能降低高并发吞吐。

**缓解**：
- 重构前后用 `BenchmarkPipeline_Throughput` 对比，性能下降 ≤ 20% 可接受
- 如果下降 > 20%，回退到 PR-2 中的备选方案：`atomic.Pointer[Record]` + seqlock

### 7.2 测试覆盖率无法短期达到 80%

**风险**：proxy.go 等模块代码量大，单 PR 补全所有分支困难。

**缓解**：
- 本次仅设 50% 基线，不强制阻断
- 在 spec 中明确列出未覆盖路径，留待阶段二补全

### 7.3 前端 UI 改动无自动化测试

**风险**：拦截规则面板、Headers 编辑器只能手动测。

**缓解**：
- 后端 API 已有测试覆盖
- 提供手动测试 checklist（见 6.1）
- 考虑阶段二引入 Playwright

### 7.4 v0.0.2 → v0.1.0 版本号跨越

**风险**：用户可能误以为是重大版本升级。

**缓解**：
- CHANGELOG 明确说明 v0.1.0 是 v0.0.2 的稳定性延续
- README 顶部加「推荐升级」标记
- 提供 v0.0.2 → v0.1.0 升级指南（无破坏性变更，直接替换二进制即可）
